# Software Module Design

## Purpose

当用户进行软件模块设计时，按照下述流程逐步推进，确保设计始终贴合用户目标。每次给用户的回复都用加粗的字体在末尾附带一句下一步准备干嘛。

## Instructions

该流程通过多轮沟通逐步确认需求和 Review 意见，不要一次性假设并完成全部设计。

## Workflow

严格按照下述步骤来完成一个模块的详细设计，如果用户跳步了则显示提醒用户并向用户发起确认。

在第一次给用户回复消息时，顺便带上预期的工作流程，简洁罗列出即可。

### Phase 1：确认需求

用户最初的需求可能并不清晰，甚至可能只是一个尚未想明白的核心想法。因此，先理解用户输入，识别其中的模糊点、遗漏和约束，再通过提问和讨论帮助用户逐步明确需求，而不是默认用户已经想清楚了完整方案。

如果目标模块与现有模块交互，先自行查看相关代码或设计文档，再结合上下文提出问题。如果你判断不出来也可以直接问用户预期怎么和现有代码结合。

问题提出后等待用户回复，必要时继续多轮讨论，直到需求基本明确。

与用户讨论设计方案时，需要综合考虑用户提出的所有观点、约束和倾向，不能割裂地处理单个信息点。这里既包括不同轮次中提出的内容，也包括同一轮中不同小点之间的关联。当多个观点、方向或约束涉及同一个设计问题时，需要将它们放在一起统一分析，识别其中的交集、补充关系和潜在冲突，并给出同时满足这些信息的方案。

### Phase 2：输出设计文档

结合沟通结果和已查阅的代码、文档及其他资料，形成模块设计方案，并落地为 Markdown 设计文档。

文档应讲清设计思路、工作原理、关键流程、关键点、难点和目录划分，达到支撑后续开发、减少重复沟通的程度。设计中所有影响方案理解和实现的关键问题，都需要展开说明，而不是只做表面介绍。例如，一个管理模块中的无锁表，不能只说明采用 CAS 无锁设计，还应详细说明如何实现无锁、多线程如何竞争，以及不同 Case 下会发生什么。

根据模块的实际复杂度自行把握文档粒度。对于简单模块可以适当简化，避免陷入形式主义，为了形式完整而引入不必要的复杂度，增加工作量或给后续开发带来负担。

设计思路上有几个强制要求：
* **铁律**：本条为思路的最高优先级铁律，任何模块的设计都应优先采用业界常见、成熟的设计方案。只有在存在明确的需求或使用场景限制时，才允许偏离常规方案；同时必须列一个清单明确说明具体限制是什么，以及为什么这些限制导致常规方案不适用。

设计文档有几个强制的要求：
* **铁律**：本条为文档的最高优先级铁律，设计文档中的文字表达必须**清晰、直白、好读**。这里的“直白”只针对语言组织和书面表达方式，**不限制专业术语、技术细节或专业描述方法的使用**；该专业的地方就应该保持专业，不能刻意简化，更不能因此丢失技术细节或方案信息。需要避免的是把原本一句很容易说明白的话写得生硬、拗口、绕弯或过度书面化，导致读者需要反复阅读才能理解。**优先使用简单、直接、自然的句式，把复杂留给技术内容本身，而不要人为增加语言上的理解成本。**
* 描述设计方案时，应尽可能先做这样一件事：脱离当前具体业务场景，从最基础、最通用的情况出发，写明白采用的纯软件设计模型是什么。先把模型本身的结构、职责和运行方式讲清楚，再结合当前场景说明具体如何落地。
* 任何版本的设计方案一定都基于了某一些前提假设，有了前提假设的约束你才会有这一版的设计方案，因此你需要在文档最开头以表格的形式列出你所基于的假设。这个前提假设表格在后续的讨论修正、版本迭代或方案更新中是持续维护的。这个前提表格中也包含某个设计偏离常规成熟方案的限制和原因。
* 文档最末尾必须有一个"讨论纪要"章节，用来记录每一次和用户的讨论内容纪要和日期，包括第一次初始方案的讨论。就像常见的会议纪要一样记录，一次会议是一个单元，里面写了多条这次会议的结论点。严禁流水账般的记录。
* 尽量在设计文档中多用图这类信息密度高的方式。
* 本阶段关注方案设计，非必要不写具体代码。

输出后等待用户 Review，并根据意见修改。用户确认通过后再进入下一阶段。

### Phase 3：关联模块改动

启动多个 SubAgent 来翻阅现有项目中的文档和代码等资料，确认当前新增模块会影响到哪些现有模块的设计或者接口，然后列举出受影响的模块，并说明哪里受影响以及修改方案（包括代码和文档）。

这一步以临时 Markdown 文件的形式输出内容，输出后等待用户 Review 和讨论，后续实整个实现和测试完成后需要删除。

### Phase 4：修改受影响模块的文档

如果当前设计不影响到其他模块，则可以跳过。

将上一步受影响模块的变动修改到其对应的设计文档中。

修改时必须保证全文口径一致。若方案从 A 调整为 B，应直接修改文中所有与方案 A 相关的内容，使全文统一采用方案 B，而不是保留前文的方案 A，再在后文追加“改为方案 B”的说明。但不要直接删除原有文档后整体重写，而是应该逐个检查现有文档，判断本轮方案修改具体影响了哪些内容、应该修改哪些位置，再针对对应部分进行准确更新。

输出后等待用户 Review，并根据意见修改。用户确认通过后再进入下一阶段。

### Phase 5：补充接口设计

在用户确认设计方案后，从代码实现层面在设计文档中追加“接口设计”章节，至少包括：

* 对外接口：给出签名，并描述处理流程，不写内部实现。
* 私有函数：给出签名，并描述处理流程，不写内部实现。
* 模块变量：给出名称、类型和用途。

如果有其他受影响的模块，则需要在其文档中补充新接口的设计。

### Phase 6：设计测试文档

在这个 SKILL 的同级目录下有一个测试用例设计指南 `test-case/`，根据这个指南的要求撰写测试文档。

### Phase 7：Review 方案设计

启动一个全新的 SubAgent，用来审查当前的方案设计。

将以下数据输入给 SubAgent：

* 用户的初始输入和后续对需求的补充讨论
* 目标模块设计文档
* 受影响模块的改动说明
* 测试文档

SubAgent 返回后根据其 Review 意见进行修改

### Phase 8：开始实现

这一步开始实现工作，包括当前模块的代码和测试用例、关联模块的文档/代码/测试用例。

实现代码时需要添加足够详细的注释，原则上平均每 5～15 行代码至少有一处注释。注释应清晰、直白地说明这段代码在做什么、为什么这样做，以及必要的上下文信息。即使是没有参与方案讨论、不了解设计背景，或者刚接手代码的同事，也应该能够仅通过代码和注释理解主要实现逻辑。同时，注释不要为了“详细”而写得冗余、冗长：简单直观的逻辑应简短说明，复杂、反直觉或依赖背景知识的部分再进行详细解释。

如果当前项目已经有日志系统，则代码实现时需要有日志打印，方便后期调试。

### Phase 9：测试和调试

执行上一步新增和修改的测试用例（包括当前模块和受关联的模块），并对失败项进行调试和解决。

失败调试时，优先使用日志来定位问题点。
