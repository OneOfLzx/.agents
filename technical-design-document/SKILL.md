# Technical Design Document

设计文档的目标不是写得多，而是：

> **让一个不了解上下文的人，也能比较轻松地理解整个方案，并足以支撑后续开发，避免实现过程中反复确认设计细节。**

设计文档必须同时做到：

> **看得懂，能落地。**

本 Skill 适用于：

* 从零设计新框架
* 在现有框架中新增模块
* 修改现有框架
* 修改现有模块

始终以降低读者**理解和实现方案的成本**为目标。

---

# 1. 先把方案设计简单

设计文档首先是“设计”，其次才是“文档”。

方案本身越复杂，越难讲清楚。

## 1.1 方案尽量简单

能用简单方案满足需求，就不要为了“更通用”“更先进”或未来可能出现的需求增加不必要的：

* 抽象
* 层级
* 状态
* 扩展机制

> **优先简单，而不是优先聪明。**

## 1.2 优先成熟方案

已有成熟、标准、团队熟悉的方案能解决问题时，不要自创机制。

如果因为特殊需求或约束必须偏离成熟方案，要说明限制条件和偏离原因。

## 1.3 优先复用

标准库、成熟组件、已有基础设施能解决的问题，不要重复造轮子。

自己实现意味着承担额外的边界情况、兼容性、Bug 和维护成本。

> **优先成熟，优先复用。**

---

# 2. 使用推荐的设计文档结构

默认按照下面的结构组织：

> **前提假设 → 背景和目标 → 整体方案 → 核心流程 → 详细设计 → 关键设计 → 异常和边界场景 → 讨论纪要**

其中：

* **前提假设**和**讨论纪要**为固定章节。
* 其余章节根据设计复杂度取舍。
* 简单设计可以合并或省略部分章节。
* 不要为了形式完整制造无意义的工作量。

整体思路是：

> **先明确方案成立的条件，再说明问题；先建立整体认识，再进入运行流程和内部设计；先讲主干，再讲复杂节点和异常分支。**

## 2.1 前提假设

任何方案都是在一组前提、假设和约束下成立的。

设计文档最开始必须列出：

> **当前方案成立所基于的重要前提和约束。**

使用单列表格，例如：

| 前提假设 / 约束        |
| ---------------- |
| 请求量预计不超过 xxx QPS |
| 允许秒级处理延迟         |
| 必须兼容现有 xxx 协议    |
| 不允许修改现有 xxx 模块   |

如果方案因为特殊限制偏离了常见成熟方案，也需要记录相关限制和原因。

随着需求、讨论和方案变化，持续维护这张表。

> **当前方案是在这些约束条件下推导出来的。**

前提发生变化时，重新检查方案是否仍然成立。

## 2.2 背景和目标

说明：

* 为什么要做
* 当前有什么问题
* 这次准备解决什么

让读者先知道：

> **我们到底在解决什么问题。**

## 2.3 整体方案

整体方案要让读者快速建立整个设计的认知地图，至少讲清楚：

* 有哪些核心部分
* 各自负责什么
* 它们之间是什么关系
* 整体怎么工作
* 核心设计思路是什么

根据设计类型调整“整体”的范围：

* 从零设计框架：先讲整个框架
* 新增模块：先讲新模块在现有系统中的位置，再讲模块内部
* 修改已有设计：重点讲清修改前、变化点和修改后

修改类设计不需要重新介绍整个旧系统，优先突出：

> **什么变了，什么没变。**

必要时使用：

> **Before → Change → After**

判断这一节是否写清楚：

> **读者只看这一节，能不能大致复述整个方案，以及这次主要设计或修改了什么？**

## 2.4 核心流程

整体方案之后，带读者完整走一遍最重要的正常流程。

例如：

> 请求进入 → 创建任务 → 进入队列 → Worker 执行 → 更新状态

主要讲清楚：

* 从哪里开始
* 接下来发生什么
* 每一步由谁负责
* 数据和状态如何变化
* 最后如何结束

涉及多个模块时，优先使用流程图或时序图。

> **先讲清主干流程，不要一开始混入大量异常和分支。**

## 2.5 详细设计

核心流程讲清楚后，再把当前设计对象这个“黑盒”打开。

详细设计主要回答：

* 内部有哪些重要组件
* 每个组件负责什么
* 组件之间如何协作

组件粒度取决于设计对象。

例如：

> 框架 → 模块 / 服务 / 子系统
> 模块 → 子模块 / 队列 / 线程 / 状态机 / 缓存 / 关键数据结构

本质上是：

> **对当前设计对象做一层必要的结构展开。**

写到能够讲清内部结构、职责划分和运行方式，并足以支撑开发即可。

> **描述设计本身，不展开具体代码、类、函数。**

## 2.6 关键设计

把真正复杂、重要的问题单独展开，例如：

* 如何避免重复执行
* 状态如何流转
* 多线程如何竞争
* 为什么选择异步
* 为什么用 MQ 而不是 RPC

关键设计不能只写“用了什么技术”，还要说明它具体怎么工作。

例如，只写：

> 使用 CAS 实现无锁。

是不够的，还需要说明：

* CAS 操作什么
* 多线程如何竞争
* 失败后怎么办
* 不同情况分别会发生什么

> **技术名词不能代替设计说明。**

真正的“讲透”是：

> **读者不仅知道用了什么，还知道它如何工作，并足以支撑后续实现。**

## 2.7 异常和边界场景

主流程和核心设计讲清楚后，再单独讲：

* 失败
* 超时
* 重复
* 并发
* 服务重启
* 其他重要边界情况

> **主干和支路都要写，但不要混着写。**

## 2.8 讨论纪要

设计文档末尾必须保留“讨论纪要”。

记录每次重要方案讨论的：

* 日期
* 最终结论
* 方案调整
* 被否定或取消的重要设计
* 尚未确定的问题

包括第一次初始方案讨论。

每次讨论作为独立单元，只保留有价值的结论和变化，不写聊天记录或会议流水账。

目的只有一个：

> **让后来的人知道当前方案为什么逐步变成现在这样。**

# 3. 按照读者的认知顺序组织内容

有了文档结构，还要决定每一部分怎么讲。

不要按照作者脑中的分类或代码目录组织，而要按照第一次接触设计的人建立认知的顺序组织。

> **先地图，再路线，最后讲路口。**

## 3.1 先整体，再局部

不要在整体方案还没讲清楚时，马上进入模块、接口、数据结构和异常逻辑。

优先按照：

1. 整个方案怎么工作
2. 正常流程怎么运行
3. 内部设计怎么组成
4. 复杂节点怎么解决

> **不要让读者看完很多章节以后，才自己总结出整个方案。**

## 3.2 先让系统跑起来，再解释为什么

设计文档首先要帮助读者在脑中把系统“跑起来”。

优先讲清：

* 从哪里开始
* 接下来发生什么
* 每一步由谁负责
* 数据和状态如何变化
* 如何结束、退出或恢复

先回答：

> **系统怎么运行？**

再解释：

> **为什么这样设计？**

如果多个组件共同参与同一条执行链路，优先沿运行过程展开，并在对应步骤解释机制和设计选择。

只有各部分相对独立、没有明显执行顺序时，才更适合按模块组织。

目标是：

> **一个不了解上下文的人，可以顺着文档，在脑中完整运行一次系统。**

## 3.3 ## 优先选择最容易建立直觉的表达方式

描述设计对象时，优先采用**最能降低理解成本**的表达方式。

如果抽象的软件模型能够减少业务概念、帮助读者更快建立整体结构，就先脱离业务名称，讲清基础模型：

* 由哪些部分组成
* 各部分负责什么
* 相互关系是什么
* 数据或控制如何流动
* 整个模型如何运行

再说明这些部分在当前业务中分别对应什么。

如果抽象后只是增加一套新术语，并没有降低理解成本，就先讲具体业务主流程，让读者建立直觉，再提炼其中的软件模型。

核心原则是：

> **抽象必须降低理解成本，否则不要为了抽象而抽象。**

> **模型更简单，就先讲模型；业务流程更直观，就先讲业务，再提炼模型。**

这条原则适用于任何层级：

> 框架 → 框架模型
> 模块 → 模块内部模型
> 队列 → 生产、消费和调度模型
> 状态机 → 状态和转换关系
> 数据结构 → 结构和组织方式

每深入一层，都可以问：

> **从哪里开始讲，能让读者用最少的新概念理解这个设计？**


## 3.4 先主干，再支路

正常流程和异常流程都需要写，但不要混在一起。

先讲清最重要的正常路径，再处理：

* 失败
* 超时
* 重试
* 重复
* 并发竞争
* 服务重启
* 其他边界情况

> **先建立稳定的主干认知，再补充特殊情况。**

## 3.5 先给结论，再解释

重要设计点不要让读者读很久以后，才知道最终采用什么方案。

优先先说明：

> **最终怎么设计。**

然后再解释：

* 为什么这样设计
* 有哪些限制
* 为什么没有选择其他方案
* 具体机制怎么工作

> **先让读者知道答案，再帮助读者理解答案。**

# 4. 优先用图降低理解成本

结构、关系、流程和变化，如果一张图能讲清楚，就不要让读者从大量文字中自己还原。

> **能直接画清楚的，优先画出来。**

但不要为了画图而画图。

原则是：

> **结构、关系、流程、变化优先用图；简单事实直接用文字。**

## 4.1 整体结构，用整体架构图

整体架构图帮助第一次接触设计的人快速建立认知地图，主要表达：

* 核心部分
* 系统层次
* 关键关系
* 典型请求或数据的主链路

整体架构图放在“整体方案”靠前的位置。

但编写时不要过早画最终版本。

更合适的是：

> **先把完整设计展开清楚，再提炼整体架构图，最后放回整体方案前面。**

也就是：

> **最后画，前面放。**

绘制时：

1. 先确定图要回答的问题
2. 先做层级抽象
3. 先找出主链路
4. 保持统一的视觉语法
5. 区分结构和流程
6. 主动省略次要信息
7. 使用 30 秒测试：第一次接触系统的人，看图后能大致说出核心模块、系统层次和主链路

> **整体架构图不是设计的起点，而是完整设计提炼后的结果。**

## 4.2 流程和交互，用流程图或时序图

涉及多个步骤或组件交互时，优先用流程图或时序图展示：

* 谁先做什么
* 接下来发生什么
* 谁和谁交互
* 流程如何结束

图负责主干关系，文字补充关键说明。

## 4.3 关键数据结构，做结构可视化

如果数据结构本身承载重要设计，不要直接贴结构体、类定义或代码。

通过结构可视化展示：

* 由哪些部分组成
* 各部分是什么关系
* 数据如何组织
* 谁包含谁
* 谁引用谁

目标是让读者直接看到：

> **这个数据结构是什么样的。**

## 4.4 有变化过程的数据结构，做演化过程可视化

如果真正重要的是数据结构如何变化，就连续展示：

> 初始状态 → 第一次变化 → 第二次变化 → 最终状态

例如：

* 插入前 / 插入后
* 扩容前 / 扩容后
* 节点移动前 / 移动后
* 状态切换前 / 状态切换后

> **结构可视化解决“它是什么样”，演化过程可视化解决“它是怎么变化的”。**

复杂设计不要求一张图讲完，必要时拆成多张图。

## 4.5 图和文字配合

图负责结构、关系和变化，文字负责解释关键点和设计意图。

> **图先建立直观认识，文字再解释关键点。**

不要：

* 画完图就默认读者理解了所有细节
* 把图中的全部内容再用文字重复一遍

简单事实直接写文字即可。

> **优先使用图降低理解成本，但不要为了画图而画图。**

# 5. 控制设计文档的表达粒度

设计文档不是越详细越好。

原则是：

> **该简单的地方简单，该展开的地方展开，并始终停留在设计层。**

## 5.1 文字清晰、直白、好读

文字表达要：

> **清晰、直白、好读。**

“直白”只针对语言组织，不限制专业术语、技术细节和专业表达。

专业内容该专业就专业，但不要把原本容易说明白的话写得生硬、绕弯或过度书面化。

> **把复杂留给技术内容本身，不要人为增加语言上的理解成本。**

## 5.2 不要陷入代码实现细节

设计文档重点讲：

* 模块怎么划分
* 模块怎么协作
* 数据怎么流动
* 状态怎么变化
* 关键机制怎么工作
* 为什么这样设计

不展开：

* 具体代码
* 类
* 函数
* 变量
* 具体代码组织

技术机制如果本身属于设计，就需要讲清楚。

例如：

> Scheduler 和 Worker 之间通过 MQ 通信。

这是设计。

具体由哪个类发送、哪个函数消费，不属于设计文档。

> **设计文档关注设计本身，不描述代码实现。**

## 5.3 简单的地方压缩，困难的地方讲透

不要给每个模块分配相同篇幅。

简单、常规的地方一带而过，重点展开：

* 核心机制
* 反直觉设计
* 容易误解的地方
* 并发
* 状态变化
* 一致性
* 多模块交互
* 关键数据结构
* 重要边界情况

> **篇幅应该和理解难度成正比。**

简单模块可以很短，复杂模块必须讲到足以支撑实现。

不要为了形式完整平均分配篇幅，也不要为了填满模板把简单问题人为写复杂。

---

# 6. Core Principles

始终遵循：

> **方案本身尽量简单，能满足需求就够了。**

> **先整体，再局部。**

> **先给结论，再解释。**

> **简单的地方压缩，困难的地方讲透。**

归根结底：

> **把复杂的问题想清楚，再把设计讲简单。**
