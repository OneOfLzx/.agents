# Software Module Design

## Purpose

当用户需要对软件模块进行修改时，按照下述流程逐步推进，确保设计始终贴合用户目标。每次给用户的回复都用加粗的字体在末尾附带一句下一步准备干嘛。

## Instructions

该流程通过多轮沟通逐步确认需求和 Review 意见，不要一次性假设并完成全部设计。

## Workflow

严格按照下述步骤来完成对一个模块的修改工作，如果用户跳步了则显示提醒用户并向用户发起确认。

在第一次给用户回复消息时，顺便带上预期的工作流程，简洁罗列出即可。

如果用户要求快速修改，则可以跳过如下步骤：[1, 2, 5, 8]，可合并的步骤：[3, 4]。

### Phase 1：确认需求

用户最初的需求可能并不清晰，甚至可能只是一个尚未想明白的核心想法。因此，先理解用户输入，识别其中的模糊点、遗漏和约束，再通过提问和讨论帮助用户逐步明确需求，而不是默认用户已经想清楚了完整方案。

如果目标模块与现有模块交互，先自行查看相关代码或设计文档，再结合上下文提出问题。如果你判断不出来也可以直接问用户预期怎么和现有代码结合。

问题提出后等待用户回复，必要时继续多轮讨论，直到需求基本明确。

与用户讨论设计方案时，需要综合考虑用户提出的所有观点、约束和倾向，不能割裂地处理单个信息点。这里既包括不同轮次中提出的内容，也包括同一轮中不同小点之间的关联。当多个观点、方向或约束涉及同一个设计问题时，需要将它们放在一起统一分析，识别其中的交集、补充关系和潜在冲突，并给出同时满足这些信息的方案。

### Phase 2：关联模块确认

启动多个 SubAgent 来翻阅现有项目中的文档和代码等资料，确认当前当前模块的改动会影响到哪些其他模块的设计或者接口，然后列举出受影响的模块，并说明哪里受影响以及修改方案。

这一步以临时 Markdown 文件的形式输出内容，后续内容追加在这个文档中。输出后等待用户 Review 和讨论。

### Phase 3：输出设计方案

综合所有模块，设计修改方案，在 Markdown 文件中追加“设计方案”章节。

当前SKILL上一级目录有一个`technical-design-document/SKILL.md`，遵循里面的指导来撰写设计文档。

输出后等待用户 Review，并根据意见修改。用户确认通过后再进入下一阶段。

### Phase 4：补充接口设计

在用户确认设计方案后，从代码实现层面在文档中追加“接口设计”章节，至少包括：

* 对外接口：给出签名，并描述处理流程，不写代码实现。
* 私有函数：给出签名，并描述处理流程，不写代码实现。
* 模块变量：给出名称、类型和用途。

### Phase 5：设计测试文档

在这个 SKILL 的同级目录下有一个测试用例设计指南 `test-case/`，根据这个指南的要求在文档中补充测试用例。

### Phase 6：修改文档库

如果要修改的模块或者受影响的模块存在现有设计或者测试文档，则对这些文档进行修改。

将本次的修改变动修改到其对应的文档中。

修改时必须保证全文口径一致。若方案从 A 调整为 B，应直接修改文中所有与方案 A 相关的内容，使全文统一采用方案 B，而不是保留前文的方案 A，再在后文追加“改为方案 B”的说明。但不要直接删除原有文档后整体重写，而是应该逐个检查现有文档，判断本轮方案修改具体影响了哪些内容、应该修改哪些位置，再针对对应部分进行准确更新。

如果文档中存在以下内容，则持续迭代更新：
* 文档最开头的设计前提假设
* 文档最末尾的讨论纪要

输出后等待用户 Review，并根据意见修改。用户确认通过后再进入下一阶段。

### Phase 7：开始实现

这一步开始实现工作，包括当前模块的代码和测试用例、关联模块的文档/代码/测试用例。

实现代码时需要添加足够详细的注释，原则上平均每 5～15 行代码至少有一处注释。注释应清晰、直白地说明这段代码在做什么、为什么这样做，以及必要的上下文信息。即使是没有参与方案讨论、不了解设计背景，或者刚接手代码的同事，也应该能够仅通过代码和注释理解主要实现逻辑。同时，注释不要为了“详细”而写得冗余、冗长：简单直观的逻辑应简短说明，复杂、反直觉或依赖背景知识的部分再进行详细解释。

如果当前项目已经有日志系统，则代码实现时需要有日志打印，方便后期调试。

### Phase 8：测试和调试

执行上一步新增和修改的测试用例（包括当前模块和受关联的模块），并对失败项进行调试和解决。

失败调试时，优先使用日志来定位问题点。

### Phase 9：清理

将临时 Markdown 文件删除。
